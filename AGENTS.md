# Repository Guidelines

## Project Structure & Module Organization

PSX is a Windows desktop terminal built with C#, WPF, WebView2, xterm.js, and ConPTY. The root contains the application entry points and production project, `PSX.csproj`; test projects and probes live under `tests/`. Keep domain records in `Models/`, UI state in `ViewModels/`, WPF controls in `Controls/`, runtime and bridge logic in `Services/`, and native interop in `Helpers/`. The WebView frontend lives in `wwwroot/`. Configuration and visual resources belong in `psx.ini`, `theme-presets/`, `Themes/`, and `Assets/`. Release tooling is under `tools/`; documentation is under `docs/`.

## Build, Test, and Development Commands

- `dotnet build PSX.slnx` - restore packages and compile the application.
- `dotnet run --project PSX.csproj` - launch a development build on Windows.
- `dotnet format PSX.slnx --verify-no-changes` - check standard .NET formatting.
- `powershell -ExecutionPolicy Bypass -File tools/test.ps1 -Suite Fast` - run the local/CI Release build, Unit + Integration, frontend, coverage, and format gate without launching a browser.
- `powershell -ExecutionPolicy Bypass -File tools/test.ps1 -Suite Full` - add Desktop probes, the portable package smoke, locked-Chromium visual/axe checks, and dependency audits.
- `powershell -ExecutionPolicy Bypass -File tools/build-release.ps1` - create the self-contained Windows x64 package in `bin/releases/`; this may download the verified Portable Node archive but never pre-installs the ACP runtime.

Use the SDK selected by `global.json`. The release script assembles the public portable package with Kimi/Qwen/OpenCode bundled baselines and the Claude seed input; any download into `runtime/` happens later from Agent mode after explicit user confirmation.

### Agent frontend workflow

The Agent UI has one rendering path: React 19 islands built by Vite from `frontend/webview/` (shell) and `frontend/agent/src/` (Agent TS/TSX) into the committed `wwwroot/app/` output. All islands portal through one shared Agent React Root and load on demand through dynamic chunks; there is no legacy renderer or React feature flag. The toolbar has one aggregated writer, `WorkspaceToolbarController`. The template exposes a `conversation-host`, while React Conversation owns the thread and `.agent-thread-scroll`. The template exposes only a `composer-host` for Composer: one `ComposerView` owns its form and UI state, including controlled draft/IME behavior, PromptInput, attachments, slash menu, controls, submit, decision prompt and preview dialog. PromptInput's local attachment list is the sole visible source; `AttachmentBridge` maps its IDs and Files to controller upload/server IDs, and ordered snapshots define submit pairing. External draft projections use monotonic `draftToken` values and defer application until `compositionend` during IME. `ComposerController` retains command validation, Bridge actions, uploads/server IDs and restore projections, but must not write Composer-owned DOM.

After changing web frontend files, run `npm.cmd run build:web`, commit the generated output, then run `npm.cmd run verify:web`, `npm.cmd run typecheck:web`, `npm.cmd run lint:web`, and the Web tests. Do not hand-edit generated files under `wwwroot/app/`. Keep the Vite build, single-React-instance invariant, and zero-Node `dotnet build` contract unless a separate build-system decision explicitly replaces them.

### Test process safety

Run verification commands sequentially, never concurrently. In particular, do not launch typecheck, lint, Vitest, build, `verify:web`, or `tools/test.ps1` in parallel tool calls. C# tests must remain non-parallel through `[assembly: DoNotParallelize]` in `tests/PSX.Tests/MSTestSettings.cs`. The Web test harness mutates process-wide browser globals and must remain single-worker: keep `fileParallelism: false` and `maxWorkers: 1` in `tests/PSX.Web.Tests/vitest.config.ts`. The full Web gate runs every test file in its own guarded process tree through `tools/run-web-tests.ps1`; each process must exit before the next file starts, and Vitest's blob reporter owns final test/coverage merging. After an interrupted or failed Web test, confirm no test-owned `node` processes remain before retrying. Do not weaken this constraint to reduce gate duration; parallel tests have exhausted workstation memory and left orphaned processes.

## Coding Style & Naming Conventions

Use four spaces in C# and follow existing .NET conventions: `PascalCase` for types, properties, methods, and public members; `camelCase` for parameters and locals; `_camelCase` for private fields. Nullable reference types and implicit usings are enabled. Keep XAML names descriptive and JavaScript/CSS consistent with nearby modules. Preserve asynchronous patterns already used: `ConfigureAwait(false)` in service code and `Dispatcher.BeginInvoke` for fire-and-forget ViewModel collection projections. WebView messages are different: both bridges must use `WebViewJsonDispatcher`, whose returned task represents actual dispatcher delivery and whose lifecycle guard drops queued work after disposal; never post WebView JSON through a bridge-local `BeginInvoke`. Changes to bridge message types must be mirrored in both C# and `frontend/webview/src/`. On the JS side, top-level message `type` values live in `frontend/webview/src/BridgeMessages.js` (`BridgeSendType` / `BridgeEventType`); use those constants instead of string literals.

The shared WebView is an application renderer, not a browser. `WebViewHostPolicy` exclusively owns browser settings, navigation/new-window handling, permissions, context-menu filtering and download denial. Editable targets keep only the localized editing allowlist; selected text keeps copy/select-all; page/image/link browser menus and browser-owned downloads remain suppressed so runtime DOM cannot be exported through “Save page as”. Do not disable all context menus and thereby regress Terminal/Composer editing. Global shell failures install through `RuntimeDiagnostics`: only the two exact Chromium ResizeObserver delivery warnings are classified as benign, while real uncaught errors retain console diagnostics and expose one sanitized, dismissible notice without paths, stacks or session content. ResizeObserver callbacks must schedule layout writes for a later animation frame.

## Testing Guidelines

Use `tests/PSX.Tests` for C# Unit, Integration, and Desktop categories; `tests/PSX.Web.Tests` for Vitest frontend tests plus the TypeScript typecheck (`npm run typecheck:web`); `tests/PSX.TestAgent` for deterministic ACP protocol scenarios; `tests/PSX.TestNpm` for process-level ACP runtime installation scenarios; and `tests/PSX.DesktopProbe` for WinExe-hosted ConPTY checks. Name cases by behavior, such as `SaveSettings_InvalidColor_UsesFallback`. Keep every test workspace, dependency cache, diagnostic, browser, and coverage artifact under the ignored repository `TestResults/` directory; tests must never touch the user's real `%USERPROFILE%\.psx`. Runner minimums are Unit 657, Integration 107, Desktop 2, Fast 765, Full 767, and Web 379; these are discovered test totals including expanded `DataRow`s. Coverage gates are C# line 67% / branch 55% and Web line 78% / statement 75% / function 75% / branch 65%. Fast never downloads or launches Chromium; Full owns package smoke, locked-Chromium visual/axe checks, and official-registry audits. Run `tools/test.ps1 -Suite Fast` during development and `-Suite Full` before a release. Real provider login, quota, network failure, and subjective UI checks remain manual as documented in `docs/testing.md`.

## Agent Slash Command Contract

The slash-command menu is PSX's complete public command surface. A leading command is executable only when it is a PSX built-in command or appears in the current filtered ACP `available_commands_update` catalog. Reject every other leading `/command` before `session/prompt`; it must not enter busy state or be written to thread history. Slash-like text inside a normal prompt is ordinary text. Keep the JavaScript composer validation and the authoritative `AcpAgentSessionService` gate synchronized, and direct Claude Code-only interactive commands to `/terminal` instead of maintaining a command blacklist. Creating a new conversation is a Workspace Tab operation: PSX does not expose `/new`; a provider may still advertise its own ACP `/new`. `/cwd` is draft-only once per-workspace session startup locks the directory, and `/delete` deletes the bound thread and closes its Agent Workspace.

## Agent Shell Visual Contract

The always-loaded WebView shell owns the only visible application chrome: a permanent 40px full-height activity rail on the left (VS Code activity-bar style — painted surface background with a right divider border) holding the global History, create, Theme, and PSX 设置 buttons, plus a 40px `workspace-chrome` row above the column contents carrying one workspace tab strip per column, aligned exactly to each column's rect; a column with a single tab keeps the legacy nameplate look. There is no left History rail slot and no fixed 120px global action region on the right. Global overlays (create, Theme) top-align to the triggering button; column menus remain anchored to their triggering tab. Clicking 「PSX 设置」 opens a process-wide settings dialog (left nav + right content: 个人主页 / 用量 / 配置 / 下载源), not a rail-anchored popover. The WPF TabBar and WPF theme row remain hidden compatibility projections and must not become a second navigation surface. A focused column is indicated only by its active tab's highlight and the strip's focus underline; never draw a persistent border around the column, dim non-focused columns, or use colored attention/worktree dots. Agent attention is explicit text on the corresponding tab (`需确认`, `待回复`, `出错`, `已完成`). Column and chrome geometry changes are direct and unanimated; only overlays and History content may use a 120–150ms opacity/short translate transition, disabled by reduced motion.

The Agent page remains a soft workbench: `#agent-workspace-container` paints `--agent-bg`, while the global History dock and each main conversation panel are independent rounded surfaces with a full border and restrained shadow. The main panel contains its toolbar, runtime card, conversation and Composer; the conversation stays a flat continuous flow. The conversation and Composer share one reading column, centered within its column's actual content rect. Responsive presentation is based on the `.agent-panel` container, never the window viewport: at 720px and wider the toolbar and Composer are complete; at 520–719px metadata truncates and the Composer moves session mode and provider config controls into its configuration overlay while Context usage stays in the footer; at 400–519px the toolbar reduces to the cwd basename plus a ⋯ overflow entry and the Composer keeps controls in the configuration overlay with context hints hidden; below 400px columns keep their pixel floors and squeeze proportionally below their floors rather than ever hiding a column. Every flex ancestor on the Composer width path must allow shrinking with `min-width: 0`, and column content must never paint into a neighbor. Plan stays a column-local overlay and never becomes a fixed column of the layout. Every scroll container must use the shared scrollbar skin: native-scrolling nodes register their selector in `frontend/webview/src/css/agent/scrollbars.css`, while History and Plan use the shared Radix ScrollArea; never set `scrollbar-color`/`scrollbar-width`.

History rows show a per-provider brand icon resolved from the catalog `IconKey` (`claude`, `kimi`, `qwen`, `opencode`, generic `agent` fallback) — never a provider-name string check. The icon is a fixed decorative (`aria-hidden`) slot rendered from local inline SVGs (Lobe Icons static archive; no CDN, network request or new icon dependency), following `currentColor` so it tracks the theme. The runtime product version lives beside the toolbar Update button, not in a bottom status bar: the backend `RuntimeVersionSnapshot` carries user-facing `CurrentVersion`/`PendingVersion` plus `ProductName`, and `runtime_update_status` adds `versionLabel` (e.g. `Claude Code v2.1.0`, empty = render no version) and `versionDetail` (ACP/runtime technical string, tooltip-only). No version text renders when the version is unknown (no misleading `v0`/`Unknown`), and narrow shells hide the label first while keeping the Update button. The global bottom status region keeps only persistent startup warnings (for example a missing WebView2 runtime) and stays collapsed otherwise; runtime status never projects there.

## Agent Plan and History Contract

Every Agent Workspace owns one live `AgentWorkspaceController`. History is one process-wide left dock, backed by `AgentHistoryStore` and `AgentHistoryRequestBroker`, and entered through the permanent 40px WebView rail rather than a per-workspace toolbar control. The History button remains enabled from first startup through terminal-only operation and after the last Agent workspace closes; opening it lazily loads the Agent UI chunk, and history/load-thread commands fall back to the process-wide bridge when no workspace channel exists. A global History load republishes `agent_providers` before `agent_threads`, because the one-shot startup catalog may precede the WebView listener; terminal-only History must therefore show the correct provider brand icons on its first render. Opening History pushes the column tab strips and column content right so the first column's left edge lands at `40px rail + 12px gutter + historyContentWidth + 12px panel gap` — exactly `--agent-panel-gap` past the dock's right edge, for Agent panels and Terminal columns alike; it never overlays a column's content, and its persisted `preferredOpen`/width remain `psx.agent.historyDockOpen` and `psx.agent.historyDockWidth`. History keeps its persisted width and remains draggable at every window and pane width (220–420px); narrow layouts no longer fall back to a fixed dock width. When the dock push leaves too little width, `PaneLayoutController` keeps its pure-ratio allocation (pixel floors constrain only the drag clamp and sash state) and squeezes columns proportionally below their floors — it never collects or hides a column. History entries open through the shared `activate` path; its three click states live in the Workspace and Bridge Contract below.

Plan is workspace-local and follows its workspace between columns. At 520px and wider it is a content-height floating card within that column; below 520px the toolbar exposes only a summary entry and Plan opens as a column-local overlay. It never participates in column width, gains a resizer, or forms a fixed column of the layout. Plan visibility, Composer drafts, decisions and scroll state survive hide/show; History search/filter/scroll is global. Keep thread messages in the conversation only: History loading/errors and Plan state never become chat cards. `/history` opens and refreshes the global dock before the busy gate and never enters busy state or writes history. Thread-open failures remain dock-only. When changing History lifecycle payloads, update the coordinator, scoped bridge, frontend dispatcher and multi-workspace tests together.

用量、配置、用户个人主页和 DSH 下载源从 activity rail 的「PSX 设置」进入，不再占用 History dock 脚。点击设置打开一块二级设置页（左侧分类、右侧内容，后续可加项）：个人主页（目前可改显示名）、用量、配置、下载源。下载源选择 `npmjs.org`（官方）或淘宝 `npmmirror.com`。Profile, usage and config travel over process-wide `agent_global_command`s intercepted by `AgentWorkspaceCoordinator` and remain available during terminal-only startup and after the last Agent workspace closes (`profile_get`/`profile_set_name`/`profile_set_avatar`, `usage_report` / `config_report` with `cached`/`force`) answered by global events (`agent_profile`, `agent_usage_report`, `agent_config_report`) that the `UsageRequestBroker` folds into the process-wide `UsageStore`. `app_settings_snapshot` is also Agent-global so the settings dialog can own npm 源. Unlike History, every request carries a `requestId` and only the matching reply resolves it — late or superseded `agent_usage_report` / `agent_config_report` replies are dropped; a successful `profile_set_*` additionally broadcasts a requestId-less `agent_profile` that applies through a monotonic `revision` guard. Statistics semantics live in C# (`AgentUsageService`) only: exact records from each Provider's optional `IAgentUsageSource` stream into bounded per-Provider accumulators and use `input + output + cacheRead + cacheCreation` for both independently reported `today`/`last7Days`/`last30Days` totals and the fixed 365-local-day `dailyTokens` series. Providers are scanned serially; JSONL readers are bounded and must never retain the full usage history in memory. `ReadUsageSnapshot()` enumerates every thread file through a minimal streaming projection containing only provider and session identifiers; titles, messages, cwd, model names and context snapshots never enter the usage report. The second-generation wire contract exposes aggregate totals and 365-day data, a flat descriptor-driven `providers[]` with the same totals and series, structured `completeness` at both levels, and the top-level request error. Completeness reasons are fixed enum keys only; paths, package/parser versions, source keys and raw diagnostics never cross the bridge. For a `partial` Provider, “已记录” means the sum of every successfully parsed exact usage row, including rows from a session that could not be declared fully matched; completeness reasons carry that uncertainty. The overall total always shows the aggregate of successfully parsed exact rows; a non-available aggregate adds the note “统计不完整；当前总量仅包含已读取到的精确 Token。” and keeps the incomplete “全部” heatmap filter disabled. Provider rows filter only the annual heatmap, window controls change only numeric totals, and neither shared C# code nor the frontend may branch on a provider name. The「配置」tab is a separate read-only disk scan (`AgentConfigService` + optional `IAgentConfigSource` on each Provider): user-level models / MCP / skills only (never project-level files), distinct from live ACP `agent_config_options` (session Composer). Secrets never cross the bridge — env/headers/options expose key names only, URLs drop query/userinfo, stdio args mask ≥32-char alphanumeric tokens, OpenCode `auth.json` lists provider ids only, and each file read is soft-capped at 2 MiB. Usage, config and profile errors surface inside the panel or footer and never enter the conversation flow; scan failures cross the bridge only as a fixed user-safe message while detailed exceptions remain internal diagnostics.

## Workspace and Bridge Contract

The always-loaded WebView `workspace-chrome` is the only workspace switcher and may mix Terminal, Agent, and DeepSeek Harness (`DshWeb`) workspaces. The no-background invariant holds: every open workspace is exactly one tab in exactly one column — there is no "open but parked" set and no restore operation. The third kind, `DshWeb`, is not an Agent workspace: it has no Provider, Thread, ACP transport or History/usage integration. PSX owns the tab, column placement, Web container and process lifecycle of a managed `dsh web` loopback server; the DeepSeek Harness app itself owns models, keys, projects, sessions, MCP, skills, plugins and its own settings under the user's `~/.dsh`. Exactly one DSH workspace exists per PSX process (`CreateDshWebAsync` activates the already-open tab instead of duplicating); its wire kind is the explicit `dsh_web` string (`WorkspaceWireKind.ToWire`), never the enum-name lowercasing `dshweb`. The DSH surface lives in the always-loaded shell (`DshWorkspaceHost`) and must never trigger `loadAgentApp()` or receive injected PSX controls. Its dedicated bridge messages are `dsh_command` (`install | retry | stop | check_update | update | cancel_update | recheck_with_registry | retry_install_with_registry`, parsed by the Terminal bridge, not `agent_command`; `update` may carry an optional exact `version`; the two `*_with_registry` commands require `registry` = `official|npmmirror`) and `dsh_runtime_status` (C# → JS: `state`, `readyUrl` only when Ready, `currentVersion`, `updateState`, optional `updatePhase` (`downloading | validating | restarting`), optional `availableVersion`, always-present `availableVersions` array of `{ version, tags[] }` (empty when none), optional `deferredVersions` / `blockedVersions` arrays of the same shape (newest-capped; deferred = published but not carried by this PSX build, blocked = rejected by a review decision), `registryKey` / `operationRegistryKey` / `catalogRegistryKey`, typed `runtimeErrorClass` / `updateErrorClass`, and a user-safe `errorClass` string; no paths, stacks or session content). Both are shell-owned and are not Agent lifecycle types. DSH download source is a process-wide PSX setting (`official` | `npmmirror`) owned by `PsxEnvironmentSettingsCoordinator` in `~/.psx/environment.json`; the rail 「PSX 设置」 button sends `app_settings_command` (`get | set_dsh_registry`) and receives `app_settings_snapshot` (`revision`, `dshRegistry`, optional `requestId`). First install uses the seed lock plus `npm ci` (mirror allowed, no official metadata query). Updates install exclusively from repository-trusted, hash-pinned lockfiles under `tools/dsh-locks/` (`catalog.json` with entries plus `blockedVersions` + `locks/<version>/`): `tools/generate-dsh-lock.ps1` produces them under its isolation contract (pinned portable Node, official `dist.integrity` cross-check at generation time, forced `npm ci` + `dsh web` launch smoke — the smoke executes unreviewed third-party lifecycle scripts, so any catalog-writing run happens only in a disposable environment without secrets and artifacts enter the repo through Git review), `DshLockCatalogTests` and build-release (pinned catalog SHA, per-entry SHA/origin/SRI verification, and a default-fatal freshness gate requiring the newest published version above the seed to be covered by entries ∪ blockedVersions; `-SkipDshFreshnessCheck` is the only escape) are the two static gates, and the release machine never executes new package code. Existing entries are never regenerated; a same-version SRI change is a security event — refuse the install, keep the old version, investigate manually, and never refresh the catalog to accept new bytes for an existing version. The client never resolves dependencies and never queries official metadata: it copies the bundled `package.json`/`package-lock.json` verbatim into `dsh-next`, re-verifies their SHA, validates the lock through the shared `DshLockValidator` (every entry pinned to the official origin with a sha512 SRI, root SRI equal to the catalog `dshSri`), then runs `npm ci` from the selected registry via `--replace-registry-host=npmjs` — the download source changes only where tarballs come from, never validation semantics, and npm checks every tarball byte against the lock SRI. The lockfile is not a sandbox: lifecycle scripts still run during that `npm ci`, pinned to generation-time official bytes. A check queries the selected registry for published `versions` plus `dist-tags` (tags are annotations only), filters to SemVer packages that are `>=` the seed and strictly newer than the installed tree, partitions them through the lock source into installable / deferred / blocked (a corrupt catalog or artifact fails the whole check with `catalog_corrupt` and the fixed reinstall message), and lets the user pick an exact version from the installable allowlist; when nothing is installable but newer versions exist the update state is `requires_psx_update` (never `up_to_date`), update commands are refused while keeping that state, and blocked versions render as 「当前 PSX 不支持此版本」 versus deferred's 「将随 PSX 更新提供」. An update installs the selected version into `dsh-next` while the current server remains available, writes a v3 receipt (lock source + lock SHA + official SRI + actual download registry; v1/v2 receipts remain readable and v2 mirror trees still pass the startup gate through their receipt origin), validates the staged tree, then switches and restarts only the managed DSH local service; PSX itself never restarts. Cancellation is available only while downloading or validating, when the current server is still untouched; once switching begins, failure to reach Ready restores and restarts the last-known-good `dsh-current`. Closing the DSH tab never disposes the runtime (background work survives); PSX exit reaps the full process tree via a `KILL_ON_JOB_CLOSE` Job Object. `KimiWeb` (`kimi_web`) is the fourth workspace kind, on par with `DshWeb`: not an Agent workspace — no Provider, Thread, ACP transport or History/usage integration. PSX owns the tab, column placement, Web container and process lifecycle of an embedded `kimi web` loopback server (portable Node running the active Kimi entry with `web --host 127.0.0.1 --port 0 --no-open` in a PSX-owned neutral working directory, never an internal tree or a user's project); Kimi owns its own server state under the user's `~/.kimi-code`. Exactly one Kimi Web workspace exists per PSX process (`CreateKimiWebAsync` activates the already-open tab instead of duplicating); its wire kind is the explicit `kimi_web` string (`WorkspaceWireKind.ToWire`), never the enum-name lowercasing `kimiweb`. The Kimi Web surface lives in the always-loaded shell (`KimiWebWorkspaceHost`) and must never trigger `loadAgentApp()` or receive injected PSX controls. Its bridge messages are `kimi_web_command` (`stop | retry`, parsed by the Terminal bridge, not `agent_command`), `kimi_web_runtime_status` (C# → JS: `state` in `unavailable | stopped | starting | ready | stopping | failed | exited`, `readyUrl` only in Ready, plus fixed wire-safe `errorClass`/`reason` enum keys; no paths, stacks or session content) and `kimi_web_export` (url/path/sessionId only — never a token). Token contract: the ready URL's `#token=` fragment appears exactly twice on the wire — the Ready `readyUrl` field and the iframe `src`; the supervisor keeps the token in memory only (loopback `Authorization` headers for `meta`/`shutdown`/export), clears it on stop/restart/failed/exited, and never logs or persists it. `FrameOriginChanged` carries only the fragment-stripped origin into `WebViewHostPolicy`, whose `kind → currentOrigin` map atomically swaps the kimi slot on restart and re-confirms the slot before injecting frame scripts. Stop is graceful first (`POST /api/v1/shutdown` with the in-memory Bearer token), then a Job-Object Kill fallback following `RuntimeProcessCleanup` discipline. Session export is host-mediated: the injected document-start script diverts the page's export POST into a `psx-kimi-web-export` handoff, C# validates the current kimi origin plus the exact `/api/v1/sessions/{id}/export` path, refuses redirects/non-ZIP/oversized payloads, and saves atomically via a SaveFileDialog — every failure surfaces as a `workspace_notice`, never silent. Closing the Kimi Web tab never disposes the runtime (background work survives); PSX exit reaps the full process tree via a `KILL_ON_JOB_CLOSE` Job Object. Startup begins with a single column holding one terminal tab; the create button defaults to a new tab in the current column, and only the explicit "right new column" action yields two columns side by side. Terminal-only startup must provide the complete chrome without loading the lazy Agent React chunk until the user opens History. Terminal workspaces retain their ConPTY `sessionId` and Terminal bridge messages never gain an Agent `workspaceId`. `agent_global_command` is the sole workspace-free Agent bridge message and is restricted to process-wide History, profile, usage and config operations; every workspace-scoped Agent bridge message requires a valid process-local `workspaceId`, and unknown, closing and closed IDs are ignored. One Agent Workspace owns one immutable Provider, Thread, ACP transport and process tree, and workspace IDs are never persisted. The WebView column tab strips are the single visible navigation truth; the WPF TabBar is only a hidden compatibility projection and command host (its drag drop targets survive as `pane_move`), never a second navigation surface.

`WorkspaceLayoutService` is the C# truth for the requested ordered layout: at most three columns (`maxColumns: 3`), each a tab stack with its `activeTabId` and `ratio`, plus one focused column. `workspace_layout` carries `focusedColumnId` and `columns: [{columnId, tabs: [{workspaceId, kind}], activeTabId, ratio}]`; `workspace_catalog` reports `maxColumns: 3` and marks each workspace with its `columnId` and `isActiveTab` — under the no-background invariant every open workspace has a `columnId`, and there are no `availableTargetPanes` or swap entries. `workspace_layout` and `workspace_catalog` have independent monotonic revisions and may arrive in either order; missing catalog data renders a generic tab in place and later enriches it without rebuilding tab strips or dividers. Column labels are issued by C# and the frontend must never infer column numbers from the effective layout. All WebView actions are intents handled by C# (`workspace_layout_intent`, `workspace_create`, `theme_action`, `app_settings_command`); the browser must not mutate logical truth or save theme state directly. The `activate` intent has two branches: an already-open workspace — by the invariant a tab in some column — activates that tab and focuses its column; anything else opens as a new tab, defaulting to the current column and degrading into a focused-column tab when a pending `new_right` placement meets the three-column cap. History clicks reuse this same path with three states: a thread already open as a tab — even an inactive tab in a column — focuses that column and activates the tab as a pure jump (no move, no duplicate); a thread not in the layout opens as a new tab in the focused column (History is fixed to the current column and never consumes a pending "right new column" placement); and the same thread can never appear as a second open tab, deduplicated at the C# `activate` entry before any placement logic. Splitting moves a workspace's tab into a fresh right-hand column and focuses it; the source column keeps its remaining tabs, an emptied source column collapses and the new column lands one position right of the source column's original position, and the cap of three columns blocks a further split that would add a column with an explicit reason (a sole-tab source collapse adds no column and stays allowed), and splitting the single open workspace is rejected as a no-op shape — no path may create an empty column. `collapse_single` merges the layout back to one column: every other column's tabs join the focused column's tab stack tail in original column order, the focused column keeps its own active tab, and no workspace leaves the open set. Closing a tab leaves the column's other tabs (its active tab falls to the left neighbor, else right); a column emptied this way is destroyed and the remaining columns absorb its ratio, and closing the unique tab of the only column resets to the startup shape so the caller creates a fresh terminal tab — never a MRU resurrection.

The always-loaded `PaneLayoutController` owns effective pixels. Divider nodes have stable `leftColumnId|rightColumnId` identities and survive ratio previews. A drag changes only its adjacent columns, previews at most once per animation frame, cancels on pointer cancel/blur/dispose/newer layout revision, and sends one complete `pane_ratios_commit` vector on release with the snapshot `baseRevision`; the wire keeps the legacy `pane_*` names, but the id space is the column ids. C# accepts that vector only when the revision and column-id set match and every ratio is finite, positive, and sums to one; it replaces the vector atomically. Column pixel floors — Agent and Kimi Web columns 320px, DSH columns 640px (the Harness center-column minimum), Terminal columns `max(400px, 60 * measuredCellWidth + horizontalPadding)` or 480px until measured — constrain only the drag clamp and the sash at-minimum state, never the allocation. All columns allocate strictly by their requested ratio at all times: pixel floors constrain only the drag clamp and the sash at-minimum state, never the allocation — switching focus never changes any column width, and divider slots, the sash and content rects share one pure-ratio geometry. When the total width cannot satisfy the sum of floors, the ratio widths squeeze proportionally below their floors — columns are never collected, hidden, or dropped. A divider reports `data-sash-state="at-minimum"` when either side sits on its floor and is disabled (`aria-disabled`) when both sides are pinned, the cursor being the only hint; double-clicking a divider equalizes its pair. During drag Terminal wrappers follow the geometry but xterm fit and ConPTY resize are deferred; after release every visible Terminal fits/resizes once. Split capacity is double-gated: the frontend disables the "right new column" entry by pixel capacity (the requested layout's minimum-width sum plus the new column's minimum width — 400px for an Agent or Kimi Web workspace, 720px for a DSH workspace, `max(400px, 60 * measuredCellWidth + horizontalPadding)` (480px until measured) for Terminal — against available width, skipping the new-column term when the split collapses its sole-tab source column) as the first gate, a presentation-layer responsibility, while C# 3-column count validation remains the second gate. Zoom renders only the focused column's tab strip while `workspace_catalog` still reports the whole open set. Hidden Agent workspaces keep folding projections but defer React timeline rendering. Only the focused Agent pane announces live content.

Attention is typed state, not a boolean or content heuristic: `WaitingForPermission` → `permission`, `WaitingForInput` → `question`, error → `error`, and an unfocused `Running`→`Idle` transition → `completed`. Focusing, starting a new run, resolving the request, or closing clears it. Window-inactive permission/question/error states may flash/send a system notification; inside the window only short text appears on the corresponding tab. Same-git-root conflict is an edge-triggered non-blocking notice, emitted once when a conflict forms and eligible again only after it resolves; the scan counts only each column's active tab, so an inactive tab in the same column sharing the git root never raises it — switching to that tab may then edge-trigger the notice, which is intentional semantics. No status is inferred from Agent reply text and no extra model is invoked.

## Agent Provider Architecture

Agent mode uses one provider-agnostic ACP session engine instance per Agent Workspace. `AgentWorkspaceCoordinator` owns routing and global History; `AgentWorkspaceFactory` creates `AcpAgentSessionService` with the provider selected from the data-driven registry. `AcpAgentSessionService` orchestrates the run, transcript and session state; wire update parsing, tool projections, decision requests, transport lifetime and reverse terminal processes belong respectively to `AcpSessionUpdateReader`, `AcpToolStateTracker`, `AcpDecisionCoordinator`, `AcpTransportLifecycle` and `AcpTerminalRequestHandler`. The session engine must not contain provider package paths, executable names, hidden-command lists, native CLI launch commands or provider-specific ACP metadata. Provider identity and compatibility policy belong in `IAcpAgentProvider` and `IAcpProviderCompatibility`; runtime installation and `AcpProcessSpec` creation belong in `IAcpAgentRuntime`. `NpmRuntimeProcessRunner` and `StagedRuntimeStore` provide the shared npm-process and current/next-directory mechanics, while each runtime retains its own package validation, seed, executable and platform rules. `AgentRuntimeCoordinator` deduplicates shared runtime preparation while every Workspace launches an independent ACP process. Production registers four curated **Managed** providers — Claude Code, Kimi Code, Qwen Code, and OpenCode — and adding another must require only its provider/runtime implementation, DI registration and tests. Ownership shapes:

- **Claude Code** — `tools/acp-seed` in the ZIP; user-confirmed install into `runtime/acp-current`; Update stages `acp-next`.
- **Kimi Code** — full `tools/kimi` baseline in the ZIP; self-update via `runtime/kimi-current` / `kimi-next` with bundled fallback.
- **Qwen Code** — full `tools/qwen` baseline in the ZIP; self-update via `runtime/qwen-current` / `qwen-next` with bundled fallback; auto-update disabled through `QWEN_CODE_SYSTEM_SETTINGS_PATH` (never set `QWEN_HOME`).
- **OpenCode** — full `tools/opencode` baseline in the ZIP: the `opencode-windows-x64` platform package (a native Bun-compiled exe) depended on directly, never the `opencode-ai` wrapper with its postinstall placeholder; self-update via `runtime/opencode-current` / `opencode-next` with bundled fallback; auto-update disabled through `OPENCODE_DISABLE_AUTOUPDATE` (the upstream config knob is unreliable). Entry is always `<managed opencode.exe> acp` (native, no portable Node at session time). Machines without AVX2 cannot run the bundled modern binary: they install `opencode-windows-x64-baseline` into `runtime/opencode-current` after user confirmation, refresh keeps selecting the baseline variant, and startup never drops that runtime copy for a same-or-newer bundled build.

`IAgentUsageSource` (the optional `UsageSource` on `IAcpAgentProvider`) is the Provider layer's single extension point for exact usage data. `ClaudeSessionUsageSource` scans `CLAUDE_CONFIG_DIR ?? ~/.claude` JSONL strictly filtered to PSX-owned session IDs. `KimiCodeSessionUsageSource` indexes only PSX-owned ACP session IDs beneath `KIMI_CODE_HOME ?? ~/.kimi-code/sessions`, streams recognized `usage.record` entries from main and subagent wires, and refuses to guess when directories are ambiguous or a format cannot prove an exact result. `QwenCodeSessionUsageSource` scans the monthly `usage/token-usage-YYYY-MM.jsonl` files under every resolvable runtime root (`QWEN_RUNTIME_DIR`, absolute `advanced.runtimeOutputDir` from global settings, `QWEN_HOME ?? ~/.qwen`), normalizes cache/thoughts against the official `totalTokens` relations, deduplicates by record `id`, and proves completeness by one-way multiset containment of each session's `chats/<sessionId>.jsonl` assistant usage signatures against the monthly rows (auxiliary calls such as auto-title legitimately appear only in monthly); relative runtime roots or format drift degrade to `partial`/`unsupported_format`, never a fake zero. `OpencodeSessionUsageSource` opens `opencode.db` read-only (path resolved the official way: `OPENCODE_DB`, `XDG_DATA_HOME`, `~/.local/share/opencode`), gates on the verified table/column signature, projects assistant message tokens through SQLite JSON1 without materializing message bodies, recurses into `parent_id` subagent sessions, and cross-checks per-session message sums against the `session.tokens_*` aggregates. Usage parser compatibility is independent of runtime installation and updates. Usage parser compatibility is independent of runtime installation and updates. Unknown thread providers use `TranscriptOnlyAgentWorkspaceSession`; they must not hold the default Provider or Runtime and must never be restored through the default adapter. Do not add provider-name conditionals to shared Workspace/session code or expose arbitrary user-defined ACP executables.

Runtime updates are strictly user-triggered from the Agent toolbar; PSX startup only runs `PrepareForStartupAsync` to promote an already-staged directory locally and must never touch npm or the network. A click on Update performs the whole check-and-stage flow (registry version query, staging download, validation, restart-pending marker) through `AgentRuntimeCoordinator`, which single-flights per runtime, broadcasts the checking/progress/outcome lifecycle to every Workspace sharing that runtime, and keeps a process-wide outcome snapshot for Workspaces created later. Claude Code stages into `runtime/acp-next` with the `acp-current`/pointer model; Kimi / Qwen / OpenCode mirror the same current/next/pointer pattern (Kimi, Qwen and OpenCode also keep a bundled baseline fallback). OpenCode's canonical registry version source is the platform package actually being installed (`opencode-windows-x64` or `-baseline`), never the `opencode-ai` meta package. Restoring a thread uses `session/resume` when the agent advertises `sessionCapabilities.resume` (no history replay) and otherwise `session/load`, where a local transcript keeps replay in control-only mode: commands, usage, config, mode and title updates apply, content chunks are dropped.

Every managed runtime process with redirected output must finish its process-tree and pipe cleanup before a cancellation or timeout result is returned. Use the shared `RuntimeProcessCleanup` path for npm installs and smoke checks; a bare `Kill(entireProcessTree: true)` followed by an immediate return can leave `runtime/*-current` or `runtime/*-next` locked on Windows. Cancellation remains `Cancelled`, timeout remains `Failed`, and cleanup diagnostics stay in the runtime log.

## Commit & Pull Request Guidelines

The existing commit history uses short, imperative subjects (for example, `Fix ACP session shutdown` or `Add unified agent workspaces`); follow that convention and keep commits focused. Pull requests targeting `dev` or `main` trigger the CI test gate defined in `.github/workflows/test.yml`, so ensure the fast suite passes before requesting review. Pull requests should explain the problem and solution, list verification steps, link related issues, and include screenshots or recordings for UI changes. Call out changes to runtime packaging, `psx.ini`, or the implicit C#/JavaScript bridge contract.

## Security & Configuration Tips

Do not commit generated `bin/`, `obj/`, runtime downloads, logs, or user data from `%USERPROFILE%\.psx\`. Never place secrets in `psx.ini` or frontend assets.
