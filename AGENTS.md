# Repository Guidelines

## Project Structure & Module Organization

PSX is a Windows desktop terminal built with C#, WPF, WebView2, xterm.js, and ConPTY. The root contains the application entry points and production project, `PSX.csproj`; test projects and probes live under `tests/`. Keep domain records in `Models/`, UI state in `ViewModels/`, WPF controls in `Controls/`, runtime and bridge logic in `Services/`, and native interop in `Helpers/`. The WebView frontend lives in `wwwroot/`. Configuration and visual resources belong in `psx.ini`, `theme-presets/`, `Themes/`, and `Assets/`. Release tooling is under `tools/`; documentation is under `docs/`.

## Build, Test, and Development Commands

- `dotnet build PSX.slnx` - restore packages and compile the application.
- `dotnet run --project PSX.csproj` - launch a development build on Windows.
- `dotnet format PSX.slnx --verify-no-changes` - check standard .NET formatting.
- `powershell -ExecutionPolicy Bypass -File tools/test.ps1 -Suite Fast` - run the local/CI unit, integration, frontend, coverage, format, and Release build gate.
- `powershell -ExecutionPolicy Bypass -File tools/test.ps1 -Suite Full` - add WPF/ConPTY desktop probes and validate the portable Release package.
- `powershell -ExecutionPolicy Bypass -File tools/build-release.ps1` - create the self-contained Windows x64 package in `bin/releases/`; this may download the verified Portable Node archive but never pre-installs the ACP runtime.

Use the SDK selected by `global.json`. The release script assembles the public portable package; users install the Agent runtime later from Agent mode after explicit confirmation.

### Agent frontend workflow

The Agent UI has one rendering path: React 19 islands built by Vite from `frontend/webview/` (shell) and `frontend/agent/src/` (Agent TS/TSX) into the committed `wwwroot/app/` output. All islands portal through one shared Agent React Root and load on demand through dynamic chunks; there is no legacy renderer or React feature flag. The toolbar has one aggregated writer, `WorkspaceToolbarController`. The template exposes a `conversation-host`, while React Conversation owns the thread and `.agent-thread-scroll`. The template exposes only a `composer-host` for Composer: one `ComposerView` owns its form and UI state, including controlled draft/IME behavior, PromptInput, attachments, slash menu, controls, submit, decision prompt and preview dialog. PromptInput's local attachment list is the sole visible source; `AttachmentBridge` maps its IDs and Files to controller upload/server IDs, and ordered snapshots define submit pairing. External draft projections use monotonic `draftToken` values and defer application until `compositionend` during IME. `ComposerController` retains command validation, Bridge actions, uploads/server IDs and restore projections, but must not write Composer-owned DOM.

After changing web frontend files, run `npm.cmd run build:web`, commit the generated output, then run `npm.cmd run verify:web`, `npm.cmd run typecheck:web`, `npm.cmd run lint:web`, and the Web tests. Do not hand-edit generated files under `wwwroot/app/`. Keep the Vite build, single-React-instance invariant, and zero-Node `dotnet build` contract unless a separate build-system decision explicitly replaces them.

### Test process safety

Run verification commands sequentially, never concurrently. In particular, do not launch typecheck, lint, Vitest, build, `verify:web`, or `tools/test.ps1` in parallel tool calls. C# tests must remain non-parallel through `[assembly: DoNotParallelize]` in `tests/PSX.Tests/MSTestSettings.cs`. The Web test harness mutates process-wide browser globals and must remain single-worker: keep `fileParallelism: false` and `maxWorkers: 1` in `tests/PSX.Web.Tests/vitest.config.ts`. After an interrupted or failed Web test, confirm no test-owned `node` processes remain before retrying. Do not weaken this constraint to reduce gate duration; parallel tests have exhausted workstation memory and left orphaned processes.

## Coding Style & Naming Conventions

Use four spaces in C# and follow existing .NET conventions: `PascalCase` for types, properties, methods, and public members; `camelCase` for parameters and locals; `_camelCase` for private fields. Nullable reference types and implicit usings are enabled. Keep XAML names descriptive and JavaScript/CSS consistent with nearby modules. Preserve asynchronous patterns already used: `ConfigureAwait(false)` in service code and `Dispatcher.BeginInvoke` when crossing to UI-owned state. Changes to bridge message types must be mirrored in both C# and `frontend/webview/src/`. On the JS side, top-level message `type` values live in `frontend/webview/src/BridgeMessages.js` (`BridgeSendType` / `BridgeEventType`); use those constants instead of string literals.

## Testing Guidelines

Use `tests/PSX.Tests` for C# Unit, Integration, and Desktop categories; `tests/PSX.Web.Tests` for Vitest frontend tests plus the TypeScript typecheck (`npm run typecheck:web`); `tests/PSX.TestAgent` for deterministic ACP protocol scenarios; `tests/PSX.TestNpm` for process-level ACP runtime installation scenarios; and `tests/PSX.DesktopProbe` for WinExe-hosted ConPTY checks. Name cases by behavior, such as `SaveSettings_InvalidColor_UsesFallback`. Keep every test workspace, dependency cache, diagnostic, and coverage artifact under the ignored repository `TestResults/` directory; tests must never touch the user's real `%USERPROFILE%\.psx`. Coverage is reported but has no percentage gate yet. Run `tools/test.ps1 -Suite Fast` during development and `-Suite Full` before a release. Real provider login, quota, network failure, and subjective UI checks remain manual as documented in `docs/testing.md`.

## Agent Slash Command Contract

The slash-command menu is PSX's complete public command surface. A leading command is executable only when it is a PSX built-in command or appears in the current filtered ACP `available_commands_update` catalog. Reject every other leading `/command` before `session/prompt`; it must not enter busy state or be written to thread history. Slash-like text inside a normal prompt is ordinary text. Keep the JavaScript composer validation and the authoritative `AcpAgentSessionService` gate synchronized, and direct Claude Code-only interactive commands to `/terminal` instead of maintaining a command blacklist. Creating a new conversation is a Workspace Tab operation: PSX does not expose `/new`; a provider may still advertise its own ACP `/new`. `/cwd` is draft-only once per-workspace session startup locks the directory, and `/delete` deletes the bound thread and closes its Agent Workspace.

## Agent Shell Visual Contract

The Agent page is a soft workbench: `#agent-workspace-container` paints a lightly tinted backdrop (`--agent-bg`) while an Agent workspace is active, and two independent rounded panels float on it — the global History dock on the left and the main conversation panel. Both are free-standing blocks with a full four-side border, the shared `--agent-workspace-radius`, and a restrained lift shadow (no wide blurs or gradients). Derived layout tokens (never new INI settings) drive the frame: `--agent-workbench-gutter` (backdrop margin around each panel), `--agent-panel-gap` (space between the two panels), `--agent-workspace-radius`, and `--agent-composer-bottom-space`. There is no full-window application strip: the toolbar is an in-panel top bar (transparent over the panel surface, only a light divider). The main panel holds the toolbar, runtime card, conversation and Composer; the conversation stays a flat, continuous reading flow (no per-message frames, no extra card walls). Because the reading-column offsets are viewport (`100vw`) based, every offset subtracts the panel's own gutter/gap — keep the CSS in `shell.css` and the mirror constants in `AgentShellLayoutController.ts` (`WORKBENCH_GUTTER`, `PANEL_GAP`, `VIEWPORT_PADDING`, `READING_MAX_WIDTH`) in sync. Responsive collapse fires when `gutter + History width + panel gap + 920px reading column + right viewport padding` no longer fits; below 1000px both panels hide temporarily and manually reopened panels stay mutually exclusive. Plan MUST remain the main panel's absolutely-positioned floating card (fixed `--agent-plan-width`, no resizer) and must never become a third fixed column. Layering relies on background luminance in light themes and border + subtle luminance in dark themes (Vercel Dark included) — never lower the border contrast to fake lightness. The Composer keeps its `--agent-radius-composer` corners, the strong theme border for dark-mode visibility, and `--agent-composer-bottom-space` breathing room (reduced but never zero on narrow windows).

History rows show a per-provider brand icon resolved from the catalog `IconKey` (`claude`, `kimi`, generic `agent` fallback) — never a provider-name string check. The icon is a fixed decorative (`aria-hidden`) slot rendered from local inline SVGs (Lobe Icons static archive; no CDN, network request or new icon dependency), following `currentColor` so it tracks the theme. The runtime product version lives beside the toolbar Update button, not in a bottom status bar: the backend `RuntimeVersionSnapshot` carries user-facing `CurrentVersion`/`PendingVersion` plus `ProductName`, and `runtime_update_status` adds `versionLabel` (e.g. `Claude Code v2.1.0`, empty = render no version) and `versionDetail` (ACP/runtime technical string, tooltip-only). No version text renders when the version is unknown (no misleading `v0`/`Unknown`), and narrow shells hide the label first while keeping the Update button. The global bottom status region keeps only persistent startup warnings (for example a missing WebView2 runtime) and stays collapsed otherwise; runtime status never projects there.

## Agent Plan and History Contract

Every Agent Workspace owns one live `AgentWorkspaceController`. History is a single global left-side dock (one per page) backed by the process-wide `AgentHistoryStore` and `AgentHistoryRequestBroker`: the broker picks any live workspace's scoped bridge to send `history` loads (the `workspaceId` contract is unchanged), coalesces invalidation broadcasts, retries once on channel loss or timeout, and drops late or unsolicited `agent_threads` responses. History has a persisted `preferredOpen` state and a temporary responsive override. Plan is a workspace-local, content-height context card below the toolbar (`PlanController`, two-state visible/hidden; its runtime preference defaults to visible, and the toolbar toggle carries an unread dot while hidden). Its width is a fixed `--agent-plan-width` token — no resizer, no width persistence. Keep thread messages in the main conversation only: history lists, loading states, and history errors live in the dock and must never be appended as chat cards. Plan visibility, composer drafts, decisions and scroll state are workspace-local and survive Tab hide/show; History search/filter/scroll is global. A Thread opens in at most one Workspace (C# activates the existing one); rows carry `providerKey` and restore through their original provider. The conversation and Composer use a collision-aware reading column: they are viewport-centered at their 920px maximum while possible; with History open they move right only enough to clear the dock, never reserve a mirrored dock-width blank strip; when dock + gap + reading column + right edge no longer fit, `AgentShellLayoutController` temporarily collapses History without changing its persisted preference, and the reading column only shrinks once the viewport itself reaches its side padding. Below 1000px the controller temporarily hides both panels without changing their dock/card shapes, and manually reopened panels are mutually exclusive. A manually reopened History dock may use the remaining reading width in a constrained viewport. `/history` is a UI navigation command: recognized before the busy check, it opens the dock and refreshes through the broker, and never enters busy state or writes thread history. Persisted keys: `psx.agent.historyDockOpen`, `psx.agent.historyDockWidth` (`psx.agent.planWidth`/`psx.agent.inspectorWidth` are retired leftovers, never read). Thread-open failures surface only in the dock via the broker-free global `agent_thread_open_error` event (never as chat cards). When changing the `agent_threads`, `agent_history_error`, `agent_thread_open_error`, `agent_thread_loaded`, Workspace lifecycle or History invalidation payloads, update the coordinator, scoped bridge, frontend dispatcher and multi-workspace tests together.

The dock footer belongs to the global History dock, not to any workspace: it is a real button (`data-role="history-profile"`) showing the process-wide user profile (avatar with first-character fallback + display name from `~/.psx/profile/`) and it opens the singleton Usage panel dialog. Profile and usage travel over two global `agent_command`s intercepted by `AgentWorkspaceCoordinator` (`profile_get`/`profile_set_name`/`profile_set_avatar`, `usage_report` with `cached`/`force`) answered by two global events (`agent_profile`, `agent_usage_report`) that the `UsageRequestBroker` folds into the process-wide `UsageStore`. Unlike History, every request carries a `requestId` and only the matching reply resolves it — late or superseded `agent_usage_report` replies are dropped; a successful `profile_set_*` additionally broadcasts a requestId-less `agent_profile` that applies through a monotonic `revision` guard. Statistics semantics live in C# (`AgentUsageService`) only: each window (`today`/`last7Days`/`last30Days`) is computed independently — active threads deduplicate per window and are never summed from the daily series, turns count user messages, the 365-day series only draws the heatmap, and cache hit rate = cacheRead / (input + cacheRead + cacheCreate) with a zero denominator rendered as "—". `providerSection` rendering is purely field-driven: `exactUsage` renders a per-model token table, `contextSnapshots` renders a snapshot list that never joins the window totals, and each section's `source` status (`available`/`partial`/`unavailable` with `scannedFiles`/`skippedFiles`/`badLines`, Claude's `expectedSessions`/`matchedSessions` and a `detail` reason) badges data completeness — neither shared C# code nor the frontend may branch on a provider name. Usage and profile errors surface inside the panel or footer and never enter the conversation flow.

## Workspace and Bridge Contract

The top TabBar is the only workspace switcher and may mix Terminal and Agent workspaces. Terminal workspaces reuse their ConPTY `sessionId` and Terminal bridge messages must not gain an Agent `workspaceId`. Every Agent bridge message in both directions requires a valid process-local `workspaceId`; JavaScript sends through its scoped bridge and C# emits through `AgentWorkspaceEventSink` instead of manually appending the ID. Unknown, closing and closed workspace IDs are ignored. One Agent Workspace owns one immutable Provider, Thread, ACP transport and process tree; its working directory locks when the first session is established. Workspace IDs are never persisted or restored after application restart.

## Agent Provider Architecture

Agent mode uses one provider-agnostic ACP session engine instance per Agent Workspace. `AgentWorkspaceCoordinator` owns routing and global History; `AgentWorkspaceFactory` creates `AcpAgentSessionService` with the provider selected from the data-driven registry. The session engine must not contain provider package paths, executable names, hidden-command lists or native CLI launch commands. Provider identity and compatibility policy belong in `IAcpAgentProvider`, runtime installation and `AcpProcessSpec` creation belong in `IAcpAgentRuntime`, and `AgentRuntimeCoordinator` deduplicates shared runtime preparation while every Workspace launches an independent ACP process. Production registers two curated providers — Claude Code and Kimi Code — and adding another must require only its provider/runtime implementation, DI registration and tests. `IAgentUsageSource` (the optional `UsageSource` on `IAcpAgentProvider`) is the Provider layer's single extension point for exact usage data: Claude's `ClaudeSessionUsageSource` scans `CLAUDE_CONFIG_DIR ?? ~/.claude` JSONL strictly filtered to PSX-owned session IDs, and a provider without a source (Kimi) simply contributes no `exactUsage`. Unknown thread providers use `TranscriptOnlyAgentWorkspaceSession`; they must not hold the default Provider or Runtime and must never be restored through the default adapter. Do not add provider-name conditionals to shared Workspace/session code or expose arbitrary user-defined ACP executables.

Runtime updates are strictly user-triggered from the Agent toolbar; PSX startup only runs `PrepareForStartupAsync` to promote an already-staged directory locally and must never touch npm or the network. A click on Update performs the whole check-and-stage flow (registry version query, staging download, validation, restart-pending marker) through `AgentRuntimeCoordinator`, which single-flights per runtime, broadcasts the checking/progress/outcome lifecycle to every Workspace sharing that runtime, and keeps a process-wide outcome snapshot for Workspaces created later. Claude Code stages into `runtime/acp-next` with the `acp-current`/pointer model; Kimi Code mirrors it with `runtime/kimi-current`/`kimi-next`/`kimi-active.txt` on top of the read-only bundled `tools/kimi` baseline, which also serves as the fallback whenever the bundled version is the same or newer. Restoring a thread uses `session/resume` when the agent advertises `sessionCapabilities.resume` (no history replay) and otherwise `session/load`, where a local transcript keeps replay in control-only mode: commands, usage, config, mode and title updates apply, content chunks are dropped.

## Commit & Pull Request Guidelines

The existing commit history uses short, imperative subjects (for example, `Fix ACP session shutdown` or `Add unified agent workspaces`); follow that convention and keep commits focused. Pull requests targeting `dev` or `main` trigger the CI test gate defined in `.github/workflows/test.yml`, so ensure the fast suite passes before requesting review. Pull requests should explain the problem and solution, list verification steps, link related issues, and include screenshots or recordings for UI changes. Call out changes to runtime packaging, `psx.ini`, or the implicit C#/JavaScript bridge contract.

## Security & Configuration Tips

Do not commit generated `bin/`, `obj/`, runtime downloads, logs, or user data from `%USERPROFILE%\.psx\`. Never place secrets in `psx.ini` or frontend assets.
