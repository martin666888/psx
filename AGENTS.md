# Repository Guidelines

## Project Structure & Module Organization

PSX is a Windows desktop terminal built with C#, WPF, WebView2, xterm.js, and ConPTY. The root contains the application entry points and production project, `PSX.csproj`; test projects and probes live under `tests/`. Keep domain records in `Models/`, UI state in `ViewModels/`, WPF controls in `Controls/`, runtime and bridge logic in `Services/`, and native interop in `Helpers/`. The WebView frontend lives in `wwwroot/`. Configuration and visual resources belong in `psx.ini`, `theme-presets/`, `Themes/`, and `Assets/`. Release tooling is under `tools/`; documentation is under `docs/`.

## Build, Test, and Development Commands

- `dotnet build PSX.slnx` - restore packages and compile the application.
- `dotnet run --project PSX.csproj` - launch a development build on Windows.
- `dotnet format PSX.slnx --verify-no-changes` - check standard .NET formatting.
- `powershell -ExecutionPolicy Bypass -File tools/test.ps1 -Suite Fast` - run the local/CI unit, integration, frontend, coverage, format, and Release build gate.
- `powershell -ExecutionPolicy Bypass -File tools/test.ps1 -Suite Full` - add WPF/ConPTY desktop probes and validate the portable Release package.
- `powershell -ExecutionPolicy Bypass -File tools/build-release.ps1` - create the self-contained Windows x64 package in `bin/releases/`; this may download the verified Portable Node archive but never pre-installs the ACP runtime.

Use the SDK selected by `global.json`. The release script assembles the public portable package; users install the Agent runtime later from Agent mode after explicit confirmation.

### Agent frontend workflow

The Agent UI has one rendering path: React 19 islands built by Vite from `frontend/webview/` (shell) and `frontend/agent/src/` (Agent TS/TSX) into the committed `wwwroot/app/` output. All islands portal through one shared Agent React Root and load on demand through dynamic chunks; there is no legacy renderer or React feature flag. The toolbar has one aggregated writer, `WorkspaceToolbarController`. The template exposes a `conversation-host`, while React Conversation owns the thread and `.agent-thread-scroll`. The template exposes only a `composer-host` for Composer: one `ComposerView` owns its form and UI state, including controlled draft/IME behavior, PromptInput, attachments, slash menu, controls, submit, decision prompt and preview dialog. PromptInput's local attachment list is the sole visible source; `AttachmentBridge` maps its IDs and Files to controller upload/server IDs, and ordered snapshots define submit pairing. External draft projections use monotonic `draftToken` values and defer application until `compositionend` during IME. `ComposerController` retains command validation, Bridge actions, uploads/server IDs and restore projections, but must not write Composer-owned DOM.

After changing web frontend files, run `npm.cmd run build:web`, commit the generated output, then run `npm.cmd run verify:web`, `npm.cmd run typecheck:web`, `npm.cmd run lint:web`, and the Web tests. Do not hand-edit generated files under `wwwroot/app/`. Keep the Vite build, single-React-instance invariant, and zero-Node `dotnet build` contract unless a separate build-system decision explicitly replaces them.

### Test process safety

Run verification commands sequentially, never concurrently. In particular, do not launch typecheck, lint, Vitest, build, `verify:web`, or `tools/test.ps1` in parallel tool calls. C# tests must remain non-parallel through `[assembly: DoNotParallelize]` in `tests/PSX.Tests/MSTestSettings.cs`. The Web test harness mutates process-wide browser globals and must remain single-worker: keep `fileParallelism: false` and `maxWorkers: 1` in `tests/PSX.Web.Tests/vitest.config.ts`. After an interrupted or failed Web test, confirm no test-owned `node` processes remain before retrying. Do not weaken this constraint to reduce gate duration; parallel tests have exhausted workstation memory and left orphaned processes.

## Coding Style & Naming Conventions

Use four spaces in C# and follow existing .NET conventions: `PascalCase` for types, properties, methods, and public members; `camelCase` for parameters and locals; `_camelCase` for private fields. Nullable reference types and implicit usings are enabled. Keep XAML names descriptive and JavaScript/CSS consistent with nearby modules. Preserve asynchronous patterns already used: `ConfigureAwait(false)` in service code and `Dispatcher.BeginInvoke` when crossing to UI-owned state. Changes to bridge message types must be mirrored in both C# and `frontend/webview/src/`. On the JS side, top-level message `type` values live in `frontend/webview/src/BridgeMessages.js` (`BridgeSendType` / `BridgeEventType`); use those constants instead of string literals.

## Testing Guidelines

Use `tests/PSX.Tests` for C# Unit, Integration, and Desktop categories; `tests/PSX.Web.Tests` for Vitest frontend tests plus the TypeScript typecheck (`npm run typecheck:web`); `tests/PSX.TestAgent` for deterministic ACP protocol scenarios; `tests/PSX.TestNpm` for process-level ACP runtime installation scenarios; and `tests/PSX.DesktopProbe` for WinExe-hosted ConPTY checks. Name cases by behavior, such as `SaveSettings_InvalidColor_UsesFallback`. Keep every test workspace, dependency cache, diagnostic, and coverage artifact under the ignored repository `TestResults/` directory; tests must never touch the user's real `%USERPROFILE%\.psx`. Coverage is reported but has no percentage gate yet. Run `tools/test.ps1 -Suite Fast` during development and `-Suite Full` before a release. Real provider login, quota, network failure, and subjective UI checks remain manual as documented in `docs/testing.md`.

## Agent Slash Command Contract

The slash-command menu is PSX's complete public command surface. A leading command is executable only when it is a PSX built-in command or appears in the current filtered ACP `available_commands_update` catalog. Reject every other leading `/command` before `session/prompt`; it must not enter busy state or be written to thread history. Slash-like text inside a normal prompt is ordinary text. Keep the JavaScript composer validation and the authoritative `AcpAgentSessionService` gate synchronized, and direct Claude Code-only interactive commands to `/terminal` instead of maintaining a command blacklist. Creating a new conversation is a Workspace Tab operation: PSX does not expose `/new`; a provider may still advertise its own ACP `/new`. `/cwd` is draft-only once per-workspace session startup locks the directory, and `/delete` deletes the bound thread and closes its Agent Workspace.

## Agent Shell Visual Contract

The always-loaded WebView shell owns the only visible application chrome: a permanent 40px full-height activity rail on the left (VS Code activity-bar style — painted surface background with a right divider border) holding the global History, workspace list, create, and Theme buttons, plus a 40px `workspace-chrome` row above the pane contents carrying only the current-workspace nameplates aligned exactly to each visible pane; there is no left History rail slot and no fixed 120px global action region on the right. Global overlays (workspace list, create, Theme) anchor to the activity rail's right edge and align vertically to the triggering button; column menus remain anchored to their nameplate. The WPF TabBar and WPF theme row remain hidden compatibility projections and must not become a second navigation surface. A focused pane is indicated only by its nameplate accent underline and foreground strength; never draw a persistent border around the pane, dim non-focused panes, or use colored attention/worktree dots. Agent attention is explicit text in the nameplate and workspace list (`需确认`, `待回复`, `出错`, `已完成`). Pane and chrome geometry changes are direct and unanimated; only overlays and History content may use a 120–150ms opacity/short translate transition, disabled by reduced motion.

The Agent page remains a soft workbench: `#agent-workspace-container` paints `--agent-bg`, while the global History dock and each main conversation panel are independent rounded surfaces with a full border and restrained shadow. The main panel contains its toolbar, runtime card, conversation and Composer; the conversation stays a flat continuous flow. The conversation and Composer share one reading column, centered within the pane's actual content rect. Responsive presentation is based on the `.agent-panel` container, never the window viewport: at 720px and wider the toolbar and Composer are complete; at 520–719px metadata truncates and Composer controls may wrap; at 400–519px the toolbar reduces to the cwd basename plus More and Composer moves Mode/Model/Thinking/Context into its configuration overlay; below 400px a non-focused pane is temporarily collected by the layout engine. Every flex ancestor on the Composer width path must allow shrinking with `min-width: 0`, and pane content must never paint into a neighbor. Plan stays a pane-local overlay and never becomes a third column. Every scroll container must use the shared scrollbar skin: native-scrolling nodes register their selector in `frontend/webview/src/css/agent/scrollbars.css`, while History and Plan use the shared Radix ScrollArea; never set `scrollbar-color`/`scrollbar-width`.

History rows show a per-provider brand icon resolved from the catalog `IconKey` (`claude`, `kimi`, generic `agent` fallback) — never a provider-name string check. The icon is a fixed decorative (`aria-hidden`) slot rendered from local inline SVGs (Lobe Icons static archive; no CDN, network request or new icon dependency), following `currentColor` so it tracks the theme. The runtime product version lives beside the toolbar Update button, not in a bottom status bar: the backend `RuntimeVersionSnapshot` carries user-facing `CurrentVersion`/`PendingVersion` plus `ProductName`, and `runtime_update_status` adds `versionLabel` (e.g. `Claude Code v2.1.0`, empty = render no version) and `versionDetail` (ACP/runtime technical string, tooltip-only). No version text renders when the version is unknown (no misleading `v0`/`Unknown`), and narrow shells hide the label first while keeping the Update button. The global bottom status region keeps only persistent startup warnings (for example a missing WebView2 runtime) and stays collapsed otherwise; runtime status never projects there.

## Agent Plan and History Contract

Every Agent Workspace owns one live `AgentWorkspaceController`. History is one process-wide left dock, backed by `AgentHistoryStore` and `AgentHistoryRequestBroker`, and entered through the permanent 40px WebView rail rather than a per-workspace toolbar control. The rail remains visible when History is closed and disabled when no Agent workspace exists. Opening History pushes the pane chrome and pane content right by exactly `40px + historyContentWidth + --agent-panel-gap`; it never overlays a pane, and its persisted `preferredOpen`/width remain `psx.agent.historyDockOpen` and `psx.agent.historyDockWidth`. If the remaining width cannot satisfy visible pane minimums, `PaneLayoutController` temporarily collects the farthest non-focused panes without mutating the requested C# layout, then restores their original order and ratios when space returns.

Plan is workspace-local and follows its workspace between panes. At 520px and wider it is a content-height floating card within that pane; below 520px the toolbar exposes only a summary entry and Plan opens as a pane-local overlay. It never participates in pane width, gains a resizer, or forms a third fixed column. Plan visibility, Composer drafts, decisions and scroll state survive hide/show; History search/filter/scroll is global. Keep thread messages in the conversation only: History loading/errors and Plan state never become chat cards. `/history` opens and refreshes the global dock before the busy gate and never enters busy state or writes history. Thread-open failures remain dock-only. When changing History lifecycle payloads, update the coordinator, scoped bridge, frontend dispatcher and multi-workspace tests together.

The dock footer belongs to the global History dock, not to any workspace: it is a real button (`data-role="history-profile"`) showing the process-wide user profile (avatar with first-character fallback + display name from `~/.psx/profile/`) and it opens the singleton Usage panel dialog (title「用量与配置」, tabs「用量 | 配置」). Profile, usage and config travel over global `agent_command`s intercepted by `AgentWorkspaceCoordinator` (`profile_get`/`profile_set_name`/`profile_set_avatar`, `usage_report` / `config_report` with `cached`/`force`) answered by global events (`agent_profile`, `agent_usage_report`, `agent_config_report`) that the `UsageRequestBroker` folds into the process-wide `UsageStore`. Unlike History, every request carries a `requestId` and only the matching reply resolves it — late or superseded `agent_usage_report` / `agent_config_report` replies are dropped; a successful `profile_set_*` additionally broadcasts a requestId-less `agent_profile` that applies through a monotonic `revision` guard. Statistics semantics live in C# (`AgentUsageService`) only: exact records from each Provider's optional `IAgentUsageSource` stream into bounded per-Provider accumulators and use `input + output + cacheRead + cacheCreation` for both independently reported `today`/`last7Days`/`last30Days` totals and the fixed 365-local-day `dailyTokens` series. Providers are scanned serially; JSONL readers are bounded and must never retain the full usage history in memory. `ReadUsageSnapshot()` enumerates every thread file through a minimal streaming projection containing only provider and session identifiers; titles, messages, cwd, model names and context snapshots never enter the usage report. The second-generation wire contract exposes aggregate totals and 365-day data, a flat descriptor-driven `providers[]` with the same totals and series, structured `completeness` at both levels, and the top-level request error. Completeness reasons are fixed enum keys only; paths, package/parser versions, source keys and raw diagnostics never cross the bridge. For a `partial` Provider, “已记录” means the sum of every successfully parsed exact usage row, including rows from a session that could not be declared fully matched; completeness reasons carry that uncertainty. The overall total always shows the aggregate of successfully parsed exact rows; a non-available aggregate adds the note “统计不完整；当前总量仅包含已读取到的精确 Token。” and keeps the incomplete “全部” heatmap filter disabled. Provider rows filter only the annual heatmap, window controls change only numeric totals, and neither shared C# code nor the frontend may branch on a provider name. The「配置」tab is a separate read-only disk scan (`AgentConfigService` + optional `IAgentConfigSource` on each Provider): user-level models / MCP / skills only (never project-level files), distinct from live ACP `agent_config_options` (session Composer). Secrets never cross the bridge — env/headers/options expose key names only, URLs drop query/userinfo, stdio args mask ≥32-char alphanumeric tokens, OpenCode `auth.json` lists provider ids only, and each file read is soft-capped at 2 MiB. Usage, config and profile errors surface inside the panel or footer and never enter the conversation flow; scan failures cross the bridge only as a fixed user-safe message while detailed exceptions remain internal diagnostics.

## Workspace and Bridge Contract

The always-loaded WebView `workspace-chrome` is the only workspace switcher and may mix Terminal and Agent workspaces. Each visible pane owns one nameplate; background workspaces are available through the global workspace list. Clicking a visible workspace focuses its pane, while clicking a background workspace replaces the focused pane. Terminal-only startup must provide the complete chrome without loading the lazy Agent React chunk. Terminal workspaces retain their ConPTY `sessionId` and Terminal bridge messages never gain an Agent `workspaceId`. Every Agent bridge message requires a valid process-local `workspaceId`; unknown, closing and closed IDs are ignored. One Agent Workspace owns one immutable Provider, Thread, ACP transport and process tree, and workspace IDs are never persisted.

`WorkspaceLayoutService` is the C# truth for the requested ordered layout (at most four non-empty panes, one pane per workspace, one focused pane). `workspace_layout` and `workspace_catalog` have independent monotonic revisions and may arrive in either order; missing catalog data renders a generic nameplate in place and later enriches it without rebuilding panes or dividers. `workspace_catalog`'s `workspaces[]` carries `availableTargetPanes: [{paneId, column}]`, with `column` the 1-based column order in the requested layout, replacing the former `availableTargetPaneIds`; column labels are issued by C# and the frontend must never infer column numbers from the effective layout. All WebView actions are intents handled by C# (`workspace_layout_intent`, `workspace_create`, `theme_action`); the browser must not mutate logical truth or save theme state directly. Split is atomic: a visible workspace requires an MRU background replacement before it can move to a new right pane, a background workspace can be inserted directly, four panes block with an explicit reason, and no path may create an empty pane.

The always-loaded `PaneLayoutController` owns effective pixels. Divider nodes have stable `leftPaneId|rightPaneId` identities and survive ratio previews. A drag changes only its adjacent panes, previews at most once per animation frame, cancels on pointer cancel/blur/dispose/newer layout revision, and sends one complete `pane_ratios_commit` vector on release with the snapshot `baseRevision`. C# accepts that vector only when the revision and pane-ID set match and every ratio is finite, positive, and sums to one; it replaces the vector atomically. Agent minimum width is 400px. Terminal minimum width is `max(400px, 60 * measuredCellWidth + horizontalPadding)`, or 480px until measured. During drag Terminal wrappers follow the geometry but xterm fit and ConPTY resize are deferred; after release every visible Terminal fits/resizes once. When width is insufficient, the browser keeps the focused pane and temporarily collects the farthest non-focused pane (tie: right side), preserving C# order/ratios for restoration. Split capacity is double-gated: the frontend disables the "right new column" entry by pixel capacity (the requested layout's minimum-width sum plus the new column's minimum width against available width) as the first gate, a presentation-layer responsibility, while C# 4-column count validation remains the second gate. Collection notifies at the edge: when the collected set grows, a one-time user notice is emitted (never repeated for an unchanged set, never on restore, and zoom resizes never count as collection); the "temporarily collected" label in the workspace list is the recovery entry point. Hidden Agent workspaces keep folding projections but defer React timeline rendering. Only the focused Agent pane announces live content.

Attention is typed state, not a boolean or content heuristic: `WaitingForPermission` → `permission`, `WaitingForInput` → `question`, error → `error`, and an unfocused `Running`→`Idle` transition → `completed`. Focusing, starting a new run, resolving the request, or closing clears it. Window-inactive permission/question/error states may flash/send a system notification; inside the window only short text appears in the pane nameplate and global workspace list. Same-git-root conflict is an edge-triggered non-blocking notice, emitted once when a conflict forms and eligible again only after it resolves. No status is inferred from Agent reply text and no extra model is invoked.

## Agent Provider Architecture

Agent mode uses one provider-agnostic ACP session engine instance per Agent Workspace. `AgentWorkspaceCoordinator` owns routing and global History; `AgentWorkspaceFactory` creates `AcpAgentSessionService` with the provider selected from the data-driven registry. The session engine must not contain provider package paths, executable names, hidden-command lists or native CLI launch commands. Provider identity and compatibility policy belong in `IAcpAgentProvider`, runtime installation and `AcpProcessSpec` creation belong in `IAcpAgentRuntime`, and `AgentRuntimeCoordinator` deduplicates shared runtime preparation while every Workspace launches an independent ACP process. Production registers five curated **Managed** providers — Claude Code, Kimi Code, Qwen Code, Qoder CLI, and OpenCode — and adding another must require only its provider/runtime implementation, DI registration and tests. Ownership shapes:

- **Claude Code** — `tools/acp-seed` in the ZIP; user-confirmed install into `runtime/acp-current`; Update stages `acp-next`.
- **Kimi Code** — full `tools/kimi` baseline in the ZIP; self-update via `runtime/kimi-current` / `kimi-next` with bundled fallback.
- **Qwen Code** — full `tools/qwen` baseline in the ZIP; self-update via `runtime/qwen-current` / `qwen-next` with bundled fallback; auto-update disabled through `QWEN_CODE_SYSTEM_SETTINGS_PATH` (never set `QWEN_HOME`).
- **Qoder CLI** — `tools/qoder-seed` only in the ZIP; user-confirmed install into `runtime/qoder-current` with `--ignore-scripts`; Update stages `qoder-next`. Entry is always `node <bundle/qodercli.js> --acp` (no PATH shim authority).
- **OpenCode** — full `tools/opencode` baseline in the ZIP: the `opencode-windows-x64` platform package (a native Bun-compiled exe) depended on directly, never the `opencode-ai` wrapper with its postinstall placeholder; self-update via `runtime/opencode-current` / `opencode-next` with bundled fallback; auto-update disabled through `OPENCODE_DISABLE_AUTOUPDATE` (the upstream config knob is unreliable). Entry is always `<managed opencode.exe> acp` (native, no portable Node at session time). Machines without AVX2 cannot run the bundled modern binary: they install `opencode-windows-x64-baseline` into `runtime/opencode-current` after user confirmation, refresh keeps selecting the baseline variant, and startup never drops that runtime copy for a same-or-newer bundled build.

`IAgentUsageSource` (the optional `UsageSource` on `IAcpAgentProvider`) is the Provider layer's single extension point for exact usage data. `ClaudeSessionUsageSource` scans `CLAUDE_CONFIG_DIR ?? ~/.claude` JSONL strictly filtered to PSX-owned session IDs. `KimiCodeSessionUsageSource` indexes only PSX-owned ACP session IDs beneath `KIMI_CODE_HOME ?? ~/.kimi-code/sessions`, streams recognized `usage.record` entries from main and subagent wires, and refuses to guess when directories are ambiguous or a format cannot prove an exact result. Qwen, Qoder, and OpenCode ship with `UsageSource = null` until exact parsers exist. Usage parser compatibility is independent of runtime installation and updates. Unknown thread providers use `TranscriptOnlyAgentWorkspaceSession`; they must not hold the default Provider or Runtime and must never be restored through the default adapter. Do not add provider-name conditionals to shared Workspace/session code or expose arbitrary user-defined ACP executables.

Runtime updates are strictly user-triggered from the Agent toolbar; PSX startup only runs `PrepareForStartupAsync` to promote an already-staged directory locally and must never touch npm or the network. A click on Update performs the whole check-and-stage flow (registry version query, staging download, validation, restart-pending marker) through `AgentRuntimeCoordinator`, which single-flights per runtime, broadcasts the checking/progress/outcome lifecycle to every Workspace sharing that runtime, and keeps a process-wide outcome snapshot for Workspaces created later. Claude Code stages into `runtime/acp-next` with the `acp-current`/pointer model; Kimi / Qwen / Qoder / OpenCode mirror the same current/next/pointer pattern (Kimi, Qwen and OpenCode also keep a bundled baseline fallback). OpenCode's canonical registry version source is the platform package actually being installed (`opencode-windows-x64` or `-baseline`), never the `opencode-ai` meta package. Restoring a thread uses `session/resume` when the agent advertises `sessionCapabilities.resume` (no history replay) and otherwise `session/load`, where a local transcript keeps replay in control-only mode: commands, usage, config, mode and title updates apply, content chunks are dropped.

## Commit & Pull Request Guidelines

The existing commit history uses short, imperative subjects (for example, `Fix ACP session shutdown` or `Add unified agent workspaces`); follow that convention and keep commits focused. Pull requests targeting `dev` or `main` trigger the CI test gate defined in `.github/workflows/test.yml`, so ensure the fast suite passes before requesting review. Pull requests should explain the problem and solution, list verification steps, link related issues, and include screenshots or recordings for UI changes. Call out changes to runtime packaging, `psx.ini`, or the implicit C#/JavaScript bridge contract.

## Security & Configuration Tips

Do not commit generated `bin/`, `obj/`, runtime downloads, logs, or user data from `%USERPROFILE%\.psx\`. Never place secrets in `psx.ini` or frontend assets.
